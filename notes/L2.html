Lecture 2 — The toolchain end-to-end, then the pipeline

Student handout · FPGA-based Accelerator Design · Monsoon 2026

Scope. How the hardware HLS builds in Lecture 1 becomes a thing running on the Alveo U50 — and how your program talks to it. We cover the data-center system model (CPU/DDR, PCIe, FPGA/HBM), the full compilation + host flow, a vadd run on the U50, roofline, and pipelining a benign loop to II = 1. This handout follows the Lecture 2 slides. The first lab lands here: by the end you should be able to reproduce vadd end-to-end.

Thesis (the spine). L1 showed HLS turn C into a datapath + FSM. L2 shows how that hardware becomes a thing running on the U50 and how your program talks to it. Two ideas carry the lecture: there are two programs and two compilers — a kernel for the fabric and a host for the CPU — that meet only at runtime; and because the real "run" is a ~1-hour build, you climb a fidelity/cost ladder, catching each bug class at the cheapest rung before paying for the next.

Learning outcomes

By the end of this lecture you can:

  1. Describe the data-center FPGA system — CPU + DDR, an FPGA + HBM on a PCIe card — and the four runtime steps (allocate, copy in, launch, copy back); and contrast it with an embedded SoC (ARM + fabric on one die, shared DDR).
  2. Name the two build tracks (host via g++; kernel via Vitis HLS + v++) and say what runs where.
  3. Explain what an .xo and an .xclbin are, and that the xclbin is L1's spatial datapath frozen into a fabric configuration (bitstream + metadata).
  4. Order the verification ladder — csim → csynth → cosim → hw_emu → hw → run — and say which bug class each rung catches and roughly what it costs.
  5. Read a csynth report: clock, II, LUT/FF/DSP/BRAM.
  6. Describe the five things a host does over XRT (open, load, allocate, sync, launch/wait, sync-back) and why the sync steps are the data-movement cost.
  7. Pipeline the dot product to II = 1 on the happy path and read iteration- vs total-latency off the report.

Running example — the same vadd we run in Lab 01

out[i] = in1[i] + in2[i]. Three DRAM-backed arrays as m_axi ports, size on s_axilite, one pipelined loop. This is the Lab 01 vadd kernel verbatim — the lecture and the lab are the same artifact on purpose, and later labs reuse this exact loop.

extern "C" void vadd(const unsigned int *in1, const unsigned int *in2,
                     unsigned int *out, int size) {
#pragma HLS INTERFACE m_axi port=in1 bundle=gmem0 depth=MAX_SIZE
#pragma HLS INTERFACE m_axi port=in2 bundle=gmem1 depth=MAX_SIZE
#pragma HLS INTERFACE m_axi port=out bundle=gmem0 depth=MAX_SIZE
vadd_loop:
    for (int i = 0; i < size; i++) {
#pragma HLS PIPELINE II=1
        out[i] = in1[i] + in2[i];
    }
}

Part I — The system: a data-center FPGA

L1 lived entirely "inside the chip." L2 starts one level out — where the data lives and how it reaches the fabric. Grounding the lecture in the physical machine first makes the host's allocate/copy/launch calls obviously necessary, and it pre-loads the PCIe wall that roofline (Part IV) runs into.

The machine

  • Host: a CPU (x86-64) with DDR — ordinary server memory.
  • Card: the Alveo U50, an FPGA on a PCIe board with its own memory, HBM (8 GB, 316 GB/s). The kernel can only touch data that is in HBM.
  • Link: PCIe Gen3 ×16 ≈ 16 GB/s — the narrow door between the two memories.

A data-center FPGA is a PCIe accelerator with its own memory — the same shape as a GPU. If you have seen CUDA, this is cudaMalloc / cudaMemcpy / launch / copy-back, one-for-one.

The four runtime steps (with host code)

Each numbered step maps to one XRT call:

  1. Allocate a buffer in HBM — xrt::bo(dev, bytes, group_id)
  2. Copy inputs in (DDR → HBM) — bo.sync(XCL_BO_SYNC_BO_TO_DEVICE)
  3. Launch the kernel — auto r = krnl(...); r.wait()
  4. Copy results back (HBM → DDR) — bo.sync(XCL_BO_SYNC_BO_FROM_DEVICE)

Steps 2 and 4 cross PCIe (~16 GB/s) while HBM runs at 316 GB/s — the link is ~20× slower than device memory. Hold that thought; roofline (Part IV) puts numbers on why it matters.

Data-center vs embedded

  • Data-center (this course): a discrete PCIe card, separate HBM, explicit DMA — our lab's U50 host. Like a GPU.
  • Embedded SoC (Zynq / MPSoC): an ARM CPU on the same die as the fabric, sharing DDR — no PCIe, no copies; tight, low-latency, power-constrained.

Same HLS C, same kernel; only the system around it changes. We target the data-center U50, but the embedded world uses the same HLS — so the mechanism spans both.

Part II — Full compilation flow

The project layout — one kernel, two drivers

The lab folder names the pieces before any tooling touches them — which makes the "two programs" point concrete:

vadd/
├─ hlscribe.yaml          # platform=u50, top=vadd
└─ baseline/
   ├─ src/
   │  ├─ kernel.cpp       # the kernel   → hardware
   │  └─ host.cpp         # host program → drives the U50
   ├─ test/
   │  └─ kernel_tb.cpp    # testbench    → csim / cosim
   ├─ configs/baseline.cfg   # part · clock · files
   └─ scripts/            # env + build (hlscribe)
  • src/kernel.cpp — the kernel, synthesized to hardware.
  • test/kernel_tb.cpp — the testbench: random inputs + a software golden reference, calls the kernel like a plain function, returns 0/1. It drives csim (native C) and cosim (against the RTL) — no hardware, no host.
  • src/host.cpp — the XRT host program (Part I); needed only for the actual hardware run.
  • configs/baseline.cfg (part/clock/files), hlscribe.yaml, scripts/.

The split to internalize: verify with the testbench through cosim; the host takes over for real execution. Two drivers, two jobs — students routinely conflate them.

The mental-model shift: two programs, two compilers

This is the single biggest jump from L1. A CPU programmer thinks "compile my program and run it." On an accelerator there are two programs, built by two different compilers, that only meet at runtime:

   KERNEL  (runs on the FPGA fabric)          HOST  (runs on the CPU)
   src/kernel.cpp                             src/host.cpp
        │                                          │
        │  Vitis HLS                               │  g++  -std=c++17
        │   csim ✓   (functional)                  │   (ordinary C++;
        │   csynth   → RTL + estimates             │    links -lxrt_coreutil)
        │   cosim ✓  (RTL vs C)                     │
        ▼                                          ▼
       RTL                                       host_app
        │  v++ -c                                   │
        ▼                                          │
     vadd.xo   (compiled kernel object)            │
        │  v++ -l   ← place & route, ~1 h           │
        ▼                                          │
     vadd.xclbin  (bitstream + metadata)           │
        │                                          │
        └──────────────►  RUNTIME (XRT)  ◄─────────┘
             host_app loads the xclbin onto the U50 over PCIe,
             DMAs inputs in, launches the kernel, DMAs results back

kernel.cpp never runs on the CPU, and host.cpp never touches the fabric. They are separate builds. The lab's hlscribe build host and hlscribe build hw are literally two independent compiles.

Track 1 — the kernel: from C to bitstream

Four artifacts, in order. Each is a real file on disk:

  • RTL — Vitis HLS turns kernel.cpp into Verilog. This is L1's datapath+FSM, now real. You never hand-edit it; you read its report (next).
  • vadd.xo — v++ -c packages that RTL as a compiled kernel object (analogous to a .o): the kernel, not yet placed on any specific fabric.
  • vadd.xclbin — v++ -l links the .xo against the U50 platform and runs place & route — assigning every LUT/FF/DSP/BRAM a physical location and routing the wires. This is the ~1-hour step and the real bitstream. This file is L1's spatial layout, frozen into a configuration the fabric loads.

Note the trap in the word "link": v++ -l is not the cheap linking a CPU programmer expects — it is synthesis-to-silicon-map, the hour-long step.

Callback to L1. Remember the datapath + FSM drawn by hand in L1? csynth generates it; v++ -l bolts it onto physical fabric. The xclbin is that picture, made loadable.

Track 2 — the host: ordinary C++ that drives the card

host.cpp is plain C++ compiled by g++ — no HLS, no fabric. Its whole job is to drive the card through the XRT runtime. The full baseline host program:

#include "experimental/xrt_kernel.h"        // + xrt_device.h, xrt_bo.h
#define N 4096
int main(int argc, char** argv) {
  // --- open the device, load the bitstream ---
  auto dev  = xrt::device("0000:xx:00.1");      // U50 by BDF
  auto uuid = dev.load_xclbin(argv[1]);
  auto k    = xrt::kernel(dev, uuid, "vadd");   // name = kernel top
  // --- (1) allocate device buffers in HBM  (group_id = bank) ---
  size_t bytes = sizeof(unsigned) * N;
  auto a = xrt::bo(dev, bytes, k.group_id(0));
  auto b = xrt::bo(dev, bytes, k.group_id(1));
  auto o = xrt::bo(dev, bytes, k.group_id(2));
  // --- map buffers, fill inputs on the host ---
  auto pa = a.map<unsigned*>();
  auto pb = b.map<unsigned*>();
  auto po = o.map<unsigned*>();
  for (int i = 0; i < N; ++i) { pa[i] = i; pb[i] = 2*i + 1; }
  // --- (2) copy in · (3) launch · (4) copy out ---
  a.sync(XCL_BO_SYNC_BO_TO_DEVICE);             // DDR -> HBM
  b.sync(XCL_BO_SYNC_BO_TO_DEVICE);
  auto run = k(a, b, o, N);  run.wait();        // launch + block
  o.sync(XCL_BO_SYNC_BO_FROM_DEVICE);           // HBM -> DDR; po[] valid
}

The five beats to recognize:

  1. Open the device — xrt::device(bdf). (A gotcha lives here — see Part III.)
  2. Load the xclbin — device.load_xclbin(...) returns a UUID; then xrt::kernel(device, uuid, "vadd") (the name must match the top function).
  3. Allocate device buffers — xrt::bo(device, bytes, krnl.group_id(i)). group_id(i) picks the DRAM bank for argument i — this is where the kernel's bundle=gmem0/gmem1 becomes a physical bank choice on the host side.
  4. Sync inputs to device — bo.sync(XCL_BO_SYNC_BO_TO_DEVICE): DMA host→card over PCIe.
  5. Launch + wait — auto run = krnl(bo_in1, bo_in2, bo_out, SIZE); run.wait();
  6. Sync output back — bo.sync(XCL_BO_SYNC_BO_FROM_DEVICE), then check vs golden.

(Xilinx also ships an older OpenCL host API — clCreateBuffer / clEnqueueMigrateMemObjects / clEnqueueTask — with the same four steps, more verbose; we use the native XRT C++ API.)

Here is the point that seeds roofline (Part IV): steps 4 and 6 are data movement over PCIe; step 5 is compute. For vadd the arrays are huge and the work per element is one add — so the sync dominates. That is why vadd is memory-bound, and Part IV puts numbers on it.

The fidelity / cost ladder — the workflow discipline

This is the heart of Part II. A CPU dev edits-compiles-runs in seconds; here the real run is a ~1 h 16 m place-and-route. So you don't "just build it" — you climb a ladder of increasing fidelity and cost, where each rung catches a bug class the cheaper rungs can't, so you only pay for the next rung once you are confident.

Rung hlscribe verb What it proves Cost Catches
C sim build csim the algorithm is correct (native compile of kernel + testbench) ~33 s plain logic bugs
C synth build csynth → results HLS built hardware; gives clock, II, LUT/FF/DSP/BRAM ~65 s won't-synthesize; bad II; resource blowup
C/RTL cosim build cosim the generated RTL matches the C, cycle-accurate ~66 s HLS/interface bugs the C sim can't see
HW emulation build hw_emu → run-hw-emu the host + kernel integrate — XRT calls, DMA, bank/group_id mapping — in simulation, no card, no 1 h build ~7.5 min (build) + run wrong bank, bad buffer size, host/kernel mismatch
HW build build hw (--slurm) a real bitstream; timing closure via place & route ~1 h 16 m timing/routing failures
Run run-hw it works on the U50 ~1.3 s reality

Two teaching points on this table:

  • csim/csynth/cosim validate Track 1 only (the kernel). hw_emu is the first rung that exercises Track 2 + the handshake — the host program, XRT, DMA, and the group_id↔bundle bank mapping — without a card or the hour-long build. That is exactly why it exists: it catches the "my kernel is fine but my host talks to it wrong" class of bug cheaply.
  • The csynth rung is the bridge to Part V. When you run results you read II = 1 off the report — that is not new hardware, it is L1's schedule, measured. Hold that thought; Part V is about making II = 1 happen (and the next lecture is about when it won't).

What hlscribe runs underneath

hlscribe is a thin driver over the Vitis tools; nothing magic. The real commands, once, so the verbs are not a black box:

# csim / cosim  → the HLS front-end runner
vitis-run --mode hls --csim  --config baseline.cfg --work_dir workspace/baseline
vitis-run --mode hls --cosim --config baseline.cfg --work_dir workspace/baseline

# csynth        → v++ in HLS mode
v++ -c --mode hls --config baseline.cfg --work_dir workspace/baseline

# hw: compile the kernel object, then link+place&route to a bitstream
v++ -c -t hw --platform $PLATFORM -k vadd -o vadd_hw.xo   src/kernel.cpp
v++ -l -t hw --platform $PLATFORM      vadd_hw.xo -o vadd_hw.xclbin

# host: just g++
g++ -std=c++17 -o host_app src/host.cpp -I$XRT_INC -L$XRT_LIB -lxrt_coreutil -lpthread

The baseline.cfg is where the part, clock, and file list live — the single source of truth both vitis-run and v++ read:

part=xcu50-fsvh2104-2-e          # the U50 device

[hls]
flow_target=vitis
syn.top=vadd                     # top function
syn.file=../src/kernel.cpp       # the kernel
tb.file=../test/kernel_tb.cpp    # the testbench
clock=3.3ns                      # target period ≈ 300 MHz
clock_uncertainty=15%

# add optimization directives below this line   ←  later

The design point of the whole flow: target selection is one flag — -t hw_emu vs -t hw builds the emulation model or the real bitstream from the same sources. You change fidelity without changing code.

The BDF gotcha — open by BDF, not index

The U50 node hosts two cards: a VCK5000 (0000:yy:00.1) and our U50 (0000:xx:00.1) — note the two cards have different BDFs. XRT enumerates the VCK5000 as device index 0, so a host that calls xrt::device(0) pushes the U50 xclbin to the wrong card and XRT rejects it:

[XRT] ERROR: failed to load xclbin: Invalid argument   (err = -22)

It looks like a platform/UUID mismatch but it is device selection. Our host.cpp opens the U50 explicitly by BDF (0000:xx:00.1). The lesson: always open Alveo cards by BDF, not index. No tutorial tells you this — and reading the error carefully (-22 = device selection, not a UUID mismatch) is the real skill.

Part IV — Roofline

Roofline is a back-of-envelope model that predicts, before you optimize, whether a kernel is limited by compute or by memory. We build both ceilings from first principles off the U50 datasheet, and use them to show that vadd is hard memory-bound — so the pipelining we do next (Part V) is not what makes vadd fast.

The U50 on one slide (datasheet numbers)

Resource U50
LUTs 872,000
Registers (FF) 1,743,000
DSP slices (DSP48E2) 5,952
BRAM 1,344 blocks · 47.3 Mb (~5.9 MB)
URAM 640 blocks · 180 Mb (~22.5 MB)
HBM2 8 GB, 316 GB/s peak (201 GB/s nominal)
Fabric / power UltraScale+, 75 W max

Ceiling 1 — peak compute from DSPs

The recipe: peak = (DSP count) × (clock) × (ops per DSP per cycle) — but "ops per DSP" depends on the datatype, and that swings the answer by an order of magnitude. That is the whole lesson.

Take the fabric clock the vadd design actually hits, ~300 MHz (the lab targets 3.3 ns = 303 MHz; csynth reports 2.8 ns). One DSP48E2 does one multiply-accumulate per cycle.

  • INT8 — the DSP48E2 packs two INT8 MACs into one DSP (shared-operand trick), so ~4 ops/DSP: $$5{,}952 \times 300\times10^{6} \times 4 \;=\; 7.1\ \text{TOP/s (INT8)}$$
  • Fixed-point / integer MAC (16/32-bit) — 1 DSP = 1 MAC = 2 ops: $$5{,}952 \times 300\times10^{6} \times 2 \;=\; 3.6\ \text{TOP/s (INT MAC)}$$
  • FP32 — a float multiply costs ~3 DSPs and a float add ~2, so an FP32 FMA ≈ 5 DSPs. Effective FMA units ≈ 5,952 / 5 ≈ 1,190: $$1{,}190 \times 300\times10^{6} \times 2 \;=\; 0.71\ \text{TFLOP/s (FP32)}$$

Same silicon, ~10× apart (INT8 → FP32) just from datatype — which is exactly why FPGAs love fixed-point / low-precision, and why any vendor "peak TOPS" headline is really a statement about a datatype and a DSP clock. (Vendor slides quote more by clocking DSPs to ~600–700 MHz standalone and by INT8 packing — so the gap between our 3.6 TOP/s and a marketing number is not mysterious.)

Ceiling 2 — the memory hierarchy, not one number

Here is where the FPGA roofline differs from a CPU/GPU one. There is no single memory roof — there is a stack of them. Each on-chip memory type is distributed and parallel (hundreds of independent blocks, each with its own ports), so aggregate on-chip bandwidth is enormous. Same recipe as compute: BW = (# blocks) × (bits/block/cycle) × clock, at 300 MHz.

Tier Capacity Parallelism Aggregate BW @ 300 MHz Nature
HBM2 (off-chip) 8 GB 32 pseudo-channels 316 GB/s (201 nominal) shared, off-chip
URAM ~22.5 MB 640 blk × 2 ports × 72 b ~3.5 TB/s on-chip, banked
BRAM ~5.9 MB 1,344 blk × 72 b ~3.6 TB/s on-chip, banked
LUTRAM (distributed) ~few MB ~half of LUTs as 64×1 RAM ~10s of TB/s (trades vs logic) on-chip, fine-grained
Registers (FF) ~0.2 MB 1.74 M bits/cycle ~65 TB/s fully spatial

Read it as an inverted pyramid: from HBM down to registers, capacity falls ~40,000× but bandwidth rises ~200×. That inversion is the physical basis of the whole course. Two consequences:

  • On-chip bandwidth dwarfs HBM. BRAM+URAM alone ≈ 7 TB/s — ~22× HBM; registers ≈ 65 TB/s — ~200× HBM. If you can get data onto the chip and reuse it, you feed the datapath from a roof 1–2 orders of magnitude higher.
  • Even HBM's 316 is optimistic per kernel. It is aggregate over 32 channels; a single m_axi port sees only ~316/32 ≈ 10 GB/s. Reaching the full number needs banking across channels — the seed for a later memory lecture (multiple ports, ARRAY_PARTITION, bundling).

The optimization game, stated once: move each datum from HBM up into BRAM/URAM (or registers) once, then reuse it many times at the on-chip roof. Every later lecture is a way of climbing this pyramid — later lectures tile into BRAM, then stream through FIFOs, then put the operands in registers (systolic) — the 65 TB/s endgame.

Put them together — the ridge point

Roofline plots attainable ops/s (y) vs arithmetic intensity AI = ops per byte moved (x). Two ceilings: a slanted memory roof perf = AI × BW and a flat compute roof. They meet at the ridge AI* = peak-compute / peak-BW:

  • INT: 3.6 TOP/s ÷ 316 GB/s ≈ 11.3 ops/byte
  • FP32: 0.71 TFLOP/s ÷ 316 GB/s ≈ 2.2 FLOP/byte

Left of the ridge → memory-bound; right → compute-bound. The twist from Ceiling 2: the memory roof is whichever tier actually feeds the datapath. Compute the ridge against HBM (316 GB/s) and it sits at AI ≈ 2–11; recompute it against BRAM (~3.6 TB/s) and the slanted roof jumps ~11× — the ridge slides left, so a kernel that was memory-bound on HBM becomes compute-bound once its data lives on-chip. That move — climbing the pyramid to raise the roof — is what optimization buys you.

Where vadd lands

out[i] = in1[i] + in2[i], unsigned int = 4 B. Per output element: 1 add, and 12 bytes move (read in1 + read in2 + write out).

$$\text{AI}_\text{vadd} = \frac{1\ \text{op}}{12\ \text{B}} \approx 0.083\ \text{op/byte}$$

That is ~27× below even the FP32 ridge (2.2) — vadd is deep in the memory-bound region. Its ceiling is the memory roof:

$$\text{attainable} = \text{AI}\times\text{BW} = 0.083 \times 316\ \text{GB/s} \approx 26\ \text{Gadd/s}$$

...and only ~0.8–1 Gadd/s if it hits a single HBM channel — which our baseline does: with no [connectivity]/sp= in baseline.cfg, v++ -l defaults all three m_axi ports (gmem0/1) to HBM[0]. So the realized ceiling is ~0.8 Gadd/s until a later lecture banks the ports across channels. Against the 3.6 TOP/s compute roof, vadd uses < 1 % of the DSPs' capability. The adders are almost idle; the kernel is starving for bytes.

Punchlines to take away:

  1. Pipelining vadd to II = 1 (Part V next) does not make vadd "fast." II = 1 just means the datapath can consume one element per cycle — but the memory can't feed one element per cycle from a single port. Optimizing the compute side of a memory-bound kernel is pushing on the flat roof you are nowhere near.
  2. The only real levers for a memory-bound kernel: raise bandwidth (more HBM channels → a later lecture) or raise AI (do more compute per byte moved — fuse operations, keep data on-chip and reuse it → later lectures). You cannot out-pipeline a bandwidth wall. But vadd can't even use the on-chip pyramid: it touches each element exactly once, so there is nothing to reuse — it is pinned to the HBM roof. Contrast GEMM, where every element is reused O(N) times: tile it into BRAM once and it feeds off the ~3.6 TB/s roof — that is the 223× story we reach later. vadd is the honest counter-example: a kernel the FPGA memory hierarchy can't rescue.
  3. Second bottleneck, from Part II: the host also feeds the card over PCIe 3.0 ×16 ≈ 16 GB/s. Those bo.sync() steps move all three arrays across PCIe; for one add per element that transfer dominates end-to-end. vadd is bandwidth-bound twice over — on HBM and on PCIe.

Structural hazard — two loads, one port

There is a concrete micro-architectural reason memory structure limits the loop — and it is the payoff of the gmem0/gmem1 bundling from Part II. Pipeline the body out[i] = in1[i] + in2[i] and overlap iterations i, i+1, i+2 (stages: load in1 · load in2 · add · store):

  • Each iteration issues two loads. On one AXI port only one load goes per cycle, so at II = 1 the loads of adjacent iterations collide in the same cycle (e.g. iter i+1's in2 and iter i+2's in1 both in C3) — a structural hazard on the port. The scheduler spaces iterations out ⇒ II = 2.
  • Fix: put the inputs on separate ports — in1→gmem0, in2→gmem1 — so both loads issue every cycle ⇒ II = 1. This is exactly why the baseline bundles them apart. (out sharing gmem0 with in1 is fine — AXI read and write channels are independent, so the store doesn't fight the load.)

A taxonomy bridge for this architecture-literate audience: a structural hazard is a shared-resource stall (a port); the stall in Parts V/VI is a data hazard (the loop-carried recurrence). Same II symptom, different cause — name both.

We pipeline the dot product to II = 1 next because it teaches the mechanism cleanly — not because it is how you would speed up a memory-bound kernel. Do not over-learn "pipeline = fast."

Part V — Pipelining, the happy path

The plan: (A) open with the accumulate as a work-it-out-yourself problem — it isolates pipelining from any dependency and introduces latency / throughput / II on it; (B) tighten those into a model; (C) apply it to our running example, the integer dot product, and read II = 1 off the report; (D) hand the float twist to Part VI. Everything here is on the happy path — II = 1 works.

A. Motivating example — the accumulate

Take the Chapter-4 accumulate from the reading (Bluebook Ex. 4-3) — dout = a + b + c + d as a 3-add dependency chain, one output per iteration of the implied main loop. The compiler lowers it to three-address ops:

C1:  t1 = a  + b
C2:  t2 = t1 + c        # needs t1
C3:  t3 = t2 + d        # needs t2
C4:  write dout         # = t3    →  unpipelined: L=3, a new result every 4 clks, 1 adder

The key property, before you work it out: consecutive iterations are independent — iteration i+1 reuses nothing from iteration i. So the only question is how much hardware we spend to overlap them.

The three words you need, on this concrete picture:

  • Latency — clocks from an iteration's inputs to its result. Here the 3-add chain ⇒ L = 3. "How long one result takes."
  • Throughput — how often a finished result comes out. We count it as cycles/output (unpipelined ⇒ a result every 4 clks); the rate form is outputs/clock = 1/that, so fewer cycles/output = higher throughput. Pipelining shrinks it without shrinking latency. (Be careful: "4" is not a bigger throughput — it is the interval; the rate is 1/4.)
  • Initiation Interval (II) — the knob: clocks before the next iteration starts. II = 1 ⇒ a new iteration every clock. Overlapping iterations is what turns a result-every-4-clks into a result-every-II-clks.

Say the distinction once: latency = per-result time; throughput = result rate. The table below is exactly that distinction made numeric.

Work it out. To start a new iteration every II cycles, fill in cycles/output, adders, and pipeline stages:

Constraint Cycles / output # Adders # Pipeline stages
No pipelining 4 1 1
II = 3 3 1 1
II = 2 2 2 2
II = 1 1 3 3

(These match Bluebook Figs 4-7→4-10.)

The reveal. Seen cycle-by-cycle — no-pipe · II = 3 · II = 2 · II = 1 — the # adders = the most adds in any one column and the spacing of the w (write) cells = cycles/output. Zoom into II = 1 and at any cycle three different iterations occupy the three chain positions.

The three "aha"s:

  1. II is the throughput knob — a new result every II cycles once full.
  2. You buy throughput with area — II = 1 needs all three chain positions live at once ⇒ 3 adders; II = 2 ⇒ 2; II = 3 ⇒ 1. This is L1's binding tradeoff (share one unit vs replicate), shown dynamically.
  3. Latency is fixed at L = 3 in every row — pipelining doesn't shorten the chain, it overlaps independent copies of it. Throughput ≠ latency.

The spatial framing: II = 1 is spatial parallelism — you replicated the datapath so three iterations run side by side in space, exactly the L1 spine.

B. Tighten it into a model

Now make latency / throughput / II precise, leaning on the RISC-pipeline analogy:

  • Steady state: throughput = 1 result every II clocks — so II is the sustained rate; the "every 4 clks" from A was just II = 4 (unpipelined).
  • Ramp: the first result comes after L clocks (ramp-up); after the last iteration starts, L more clocks to drain (ramp-down). Latency is a one-time cost at the ends; II is paid every iteration.
  • Total cycles for N iterations: $$\text{total} \approx L + (N-1)\times \text{II}$$ For large N this is dominated by N·II — so II is what sets sustained performance; latency is a one-time ramp cost. (N = 1000 gives 3999 clks at II = 4 vs 1002 at II = 1 — ~4×.)
  • Report vocabulary (so you can read a real synth report next): Trip Count, Iteration Latency, Initiation Interval (II), Loop Latency.

C. Apply it — the integer dot product to II = 1

Now our running example. Drop the if from L1's Stage B and it is the dense dot product = the GEMM inner loop we optimize in later lectures:

int acc = 0;
dot: for (int i = 0; i < N; i++) {
#pragma HLS PIPELINE II=1
    acc += a[i] * b[i];        // integer/fixed-point
}

Will this hit II = 1? Two dependencies to weigh:

  • The multiply a[i]*b[i] has multi-cycle latency (say ~3 clks) — but it is not loop-carried: iteration i's product doesn't depend on i−1. It adds to iteration latency, not to II.
  • The accumulate acc = acc + product is loop-carried — i+1 needs the acc that i wrote. But with a single-cycle integer add, that feedback path closes in one clock, so a new iteration can still start every cycle.

⇒ II = 1 achievable — the happy path. The DFG says which edge is loop-carried; the timing diagram says why a 1-cycle feedback still tolerates II = 1.

Two things to trace on the integer diagram: (i) i0's staircase M1→M2→M3→A — that 4-cycle diagonal is latency (multiply depth 3 + add 1), a one-time ramp because the multiply is not loop-carried; (ii) the short feedback arcs on the A row hand acc from iteration i to i+1 in the next cycle, so a new iteration issues every clock and the A row emits one result per cycle. The multiply's latency never touches II; only the loop-carried acc does. The one-line rule to carry into Part VI:

$$\text{II} \ge \left\lceil \frac{\text{feedback-op latency}}{\text{dependence distance}} \right\rceil = \left\lceil \frac{1}{1} \right\rceil = 1.$$

On a real report you read II = 1, iteration latency = multiply depth + 1, loop latency ≈ L + (N−1) — the three numbers made concrete.

Tie back to Part IV so you don't over-learn "pipeline = fast": II = 1 means the datapath can eat one element per cycle — worth it only if memory can feed it. For a streamed kernel (vadd) it can't (memory-bound); for the reused GEMM, tiling into BRAM makes II = 1 pay off — that is the 223× we reach later.

D. Handoff to the cliffhanger

One pointed question sets up Part VI: what in the dot product decided that II = 1 was allowed? The 1-cycle feedback on acc. So: what if acc is a float?

Part VI — Cliffhanger

You just learned pipeline → II = 1 → fast. Now the one-line change that quietly breaks it — and we stop before the resolution, because the breakdown and the fix are the next lecture's whole reason to exist.

The one-line change

Same dot product, same pragma — flip the accumulator's type:

float acc = 0;                    // was: int
dot: for (int i = 0; i < N; i++) {
#pragma HLS PIPELINE II=1          // unchanged — we still *ask* for II=1
    acc += a[i] * b[i];
}

Nothing else moved. The pragma still says II = 1.

Predict it — you have the tool

Using the rule from Part V.C — II is bounded by the latency of the loop-carried feedback path — what changed?

  • Integer add closed the acc feedback in 1 clock → II = 1 was legal.
  • A float add is multi-cycle (~4 clocks on this fabric). Iteration i+1's add needs i's acc, which isn't ready for ~4 clocks — so the next iteration can't start every cycle. The feedback path now forces II ≈ 4, no matter what the pragma asks.

So the honest prediction you can make yourself: HLS cannot honor II = 1 here. It relaxes II to ~the float-add latency (and says so in the log) — the "obvious" pragma silently underdelivers ~4× on the one loop that matters.

The float diagram is deliberately the same layout as the integer one: identical M1·M2·M3 multiply block on top, so only the add block changed. In the int diagram the add was one row (1 cycle); here it is four rows (A1·A2·A3·A4). Trace i0's staircase through all seven stages (latency = 3 mul + 4 add = 7 cyc); i1 issues 4 cycles after i0. Because the accumulate is loop-carried, i1's add cannot enter A1 until i0's acc emerges from A4 — so only one iteration is ever in the adder, the other three stages sit idle, and both the multiply and adder run at 1/4 utilization. Same rule, one term changed:

$$\text{II} \ge \left\lceil \frac{\text{float-add latency}}{\text{distance}} \right\rceil = \left\lceil \frac{4}{1} \right\rceil = 4.$$

The teaching beat is the A/B: integer feedback op = 1 cycle → II = 1, next to float feedback op = 4 cycles → II = 4 — the recurrence latency, not the pragma, sets II.

Name the thing: a loop-carried dependency through a multi-cycle op is a recurrence — the reason "just add pragmas" fails. And it is not a toy: this acc is the GEMM inner product, so this recurrence is the wall standing between you and the 223×.
