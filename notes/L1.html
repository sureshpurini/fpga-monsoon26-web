Lecture 1 — Why FPGAs, why HLS C, and how HLS builds hardware

Student handout · FPGA-based Accelerator Design · Monsoon 2026

Scope. How a C program becomes hardware — the mechanism. Pipelining, the toolchain, and running on the Alveo U50 come in Lecture 2. This handout follows the Lecture 1 slides.

Thesis (the spine of the whole course). Computation has a structure — a control/data-flow graph. A CPU/GPU streams that structure through fixed hardware over time (temporal); an FPGA lays it out in space as a custom datapath + controller (spatial). "Why FPGAs" and "how HLS works" are the same idea at two zoom levels — and HLS is what turns your C's graph into that spatial layout automatically.

Learning outcomes

By the end of this lecture you can explain:

  1. Why an FPGA accelerator differs from CPU/GPU execution (spatial vs temporal).
  2. Why C code does not uniquely define hardware.
  3. What a basic block and a CFG are; what a DFG / dependence graph is.
  4. How HLS derives operations and dependences from C.
  5. The difference between scheduling, allocation, and binding.
  6. How a schedule becomes a datapath + FSM + memory/interface.
  7. Why HLS is a compiler choosing an architecture, not a C-to-Verilog translator.

Running example (built in two stages)

Stage A is pure datapath (no control flow) — the clean vehicle for scheduling and binding. Stage B adds a loop and a branch — the vehicle for the CFG and control construction. Drop the if from Stage B and you have the dense dot product = the GEMM inner loop we optimize in L2–L6. The continuity is deliberate.

// Stage A — one basic block, no control flow
z = a*b + c*d;

// Stage B — loop with a conditional (a masked / sparse MAC)
acc = 0;
for (int i = 0; i < N; i++) {
    int x = a[i];
    if (x > threshold)
        acc += x * b[i];      // multiply-accumulate on the taken path
}
*result = acc;

Part I — Why specialize, and why a high-level language

Three questions, in order: (A) why not write the hardware directly in RTL? (B) ASIC or FPGA? (C) why build custom hardware at all instead of a CPU/GPU?

A. Modern accelerators are complex — RTL alone doesn't scale

Modern accelerators (ML inference engines, video codecs, genomics, packet processors) are millions of gates: deep pipelines, many parallel units, elaborate on-chip memory. Describing that directly in RTL (Verilog/VHDL) means hand-specifying every register, wire, FSM, and cycle of timing — which is:

  • slow & costly — high lines-of-code per unit of function; months of effort;
  • error-prone — manual pipelining, hazards, handshakes;
  • hard to verify — RTL simulation is slow, bugs surface late;
  • hard to explore — a different microarchitecture means rewriting the RTL.

So the field raised the abstraction level with higher-level hardware languages:

Language Level Pros Cons
HLS C/C++ (Vitis HLS, Catapult) algorithm write the algorithm in C; big productivity jump; fast design-space exploration; C-level functional verification less direct control of microarchitecture; quality-of-results can lag hand-RTL; needs guidance (pragmas); not all C is synthesizable
Bluespec (BSV) "productive RTL" guarded atomic rules → correct-by-construction concurrency; strong static types & elaboration steeper learning curve; smaller ecosystem; you still think in hardware
Chisel RTL generator (Scala) parameterized generators; software abstractions; powers RISC-V cores (Rocket, BOOM) still structural RTL underneath; Scala learning curve

HLS C is the highest on this spectrum — you write what to compute; Chisel and Bluespec are productive RTL (still how, but safer and parameterized). This course uses HLS C — the biggest productivity jump, and the only one that lets you start from an algorithm. The price of that jump is the whole rest of the lecture: because C says nothing about cycles or hardware, a compiler must invent the microarchitecture. That compiler is HLS.

B. Where do you put it? ASIC vs FPGA

The same RTL — hand-written or emitted by HLS — can be implemented two ways:

ASIC FPGA
What custom-fabricated chip reconfigurable fabric (LUTs, FFs, DSPs, BRAM)
NRE (upfront) very high — masks, design, verification (up to $M at advanced nodes) ~zero — buy the part, reprogram freely
Per-unit cost low at volume higher
Perf / power / area best ~5–20× worse clock, more area & power
Time-to-market months–years, frozen at tape-out days; reprogrammable, bugs fixable
Best for high volume, fixed function low/medium volume, prototyping, evolving workloads

Break-even. Total cost ≈ NRE + (per-unit × volume). ASIC = high intercept, shallow slope; FPGA = ~0 intercept, steep slope. They cross at a break-even volume N*: below it FPGA is cheaper, above it ASIC wins.

Volume — plus reconfigurability and time-to-market — decides. For fast-moving workloads (ML changes faster than a ~2-year tape-out), reprogrammability itself is a reason to pick FPGA. We target FPGA: the productive, reprogrammable path — and the same HLS C can drive an ASIC flow later.

C. Why custom hardware at all? The cost of instructions

Why not just run everything on a CPU/GPU? Because a general-purpose processor spends most of its energy not on your computation. Every operation goes through fetch → decode → (schedule) → register-file → execute. For a single 32-bit add, the ALU work is a sliver of the energy; instruction supply and data movement dominate.

Representative 45 nm energy (Horowitz, Computing's Energy Problem, ISSCC 2014 — orders of magnitude, not exact):

  • 32-bit int add ≈ 0.1 pJ · 32-bit multiply ≈ 3 pJ · FP add ≈ 0.9 pJ
  • instruction fetch + decode + control ≈ tens of pJ per instruction
  • 8 KB SRAM read ≈ ~10 pJ · a DRAM access ≈ ~1000+ pJ

The arithmetic is often < 10% of the energy — the rest is overhead. (Hameed et al., ISCA 2010, measured general-purpose chips ~10–100× less efficient than a specialized datapath for the same task.) Call it a poor instruction-to-useful-work ratio, and watch each architecture attack it:

Arch Instruction model Flexibility Perf/Watt
CPU (scalar) 1 instruction → 1 op highest lowest
SIMD / GPU (SIMT) 1 instruction → N ops high medium
GPU Tensor core 1 instruction → a matrix tile medium higher
FPGA no instructions — reconfigurable datapath medium (reprogram) high
ASIC no instructions — fixed datapath none highest

SIMD/vector and Tensor cores amortize fetch/decode over more work per instruction. FPGAs/ASICs go all the way: no instruction stream — the "program" is the wiring, data flows through fixed operators every cycle, and the instruction tax goes to zero. That's why spatial hardware wins on performance per watt (ops/joule) for fixed or streaming workloads. FPGAs add two more levers: custom bit-widths (use exactly the precision you need, not 32 bits) and deterministic low-latency streaming. The cost of all this: you build hardware per workload instead of running an arbitrary program.

The thesis. A CPU/GPU streams a computation through fixed hardware over time (temporal), paying an instruction tax each step. An FPGA lays the same computation out in space as a custom datapath (spatial) and stops paying it. "Why FPGAs" and "how HLS works" are the same idea at two zoom levels — and HLS is what turns your C into that spatial layout.

Part II — "C is not hardware"

We picked HLS C for the productivity jump (Part I.A). The catch — and the reason HLS is a compiler, not a translator — is that C under-specifies the hardware. This one line:

z = a*b + c*d;

does not specify any of:

  • whether each multiply/add takes one cycle or several,
  • whether operators are shared across cycles,
  • operand bit widths,
  • pipeline depth,
  • clock frequency,
  • interface protocol.

Because C leaves all of this open, turning it into hardware is a compilation and search problem — which the rest of the lecture unpacks. (We schedule exactly this expression in Part III.)

An honest caveat that seeds the whole course: HLS won't give good hardware for free — you must guide it, and that guidance is what L2–L6 are about.

Part III — From C to hardware: a first example (Stage A)

We develop the whole mechanism on the simplest possible kernel — a single expression with no control flow — then let Stage B (Part IV) add the control-flow machinery.

z = a*b + c*d;

One basic block. A basic block is straight-line code with one entry and one exit — this whole kernel is one. HLS builds two graphs from your code: a CFG (control — which basic blocks execute) and a DFG (data — which values depend on which). With a single basic block the CFG is one node, so Stage A is a clean vehicle for the DFG, and then scheduling, allocation, binding.

The data-flow graph (DFG)

The DFG captures data dependence only: the two multiplies are independent of each other; the add needs both products. No order is imposed beyond "the add waits for its inputs" — that freedom is exactly what scheduling resolves next.

DFG = which values depend on which — the graph HLS schedules and turns into a datapath.

Scheduling, allocation, binding

Three distinct decisions — keep them separate:

  • Scheduling — which clock cycle each operation executes in.
  • Allocation — how many hardware resources exist (adders, multipliers, ports).
  • Binding — which resource executes each operation (and thus what gets shared).

Constraints on scheduling: (a) data dependences (from the DFG), (b) resource limits, (c) operation latencies. The intuition is ASAP / ALAP (as-soon- / as-late-as- possible). Real tools use SDC/LP scheduling (out of scope here); if you know VLIW / list instruction scheduling with resource constraints, it is essentially that.

Stage A schedule — the binding / sharing tradeoff

Assume a non-pipelined multiplier = 3 cycles, add = 1 cycle. The two multiplies are independent; the add needs both.

Try it yourself first: with two multipliers, how many cycles does z take? With one multiplier (shared)? Commit to an answer, then check against the tables.

Allocate 2 multipliers (the two multiplies are independent → run in parallel):

Cycle Operation(s)
1–3 m1 = a*b and m2 = c*d in parallel
4 z = m1 + m2

Latency = 4 cycles, cost = 2 multipliers + 1 adder.

Allocate 1 multiplier (share it — bind both multiplies to the same unit):

Cycle Operation(s)
1–3 m1 = a*b
4–6 m2 = c*d (reuse the multiplier, operands mux-selected)
7 z = m1 + m2

Latency = 7 cycles, cost = 1 multiplier + 1 adder + input muxes.

This is the area/latency knob (LUT/DSP vs cycles) you will later read off synthesis reports. Same C, two architectures — chosen by allocation + binding.

Part IV — Adding control flow: a second example (Stage B)

Now a kernel with control flow — a masked / sparse multiply-accumulate. Drop the if and it's the dense dot product = the GEMM inner loop optimized in L2–L6.

acc = 0;
for (int i = 0; i < N; i++) {
    int x = a[i];
    if (x > threshold)
        acc += x * b[i];
}
*result = acc;

Stage B as basic blocks

BB0  init:     acc = 0;  i = 0;                 -> BB1
BB1  cond:     if (i < N)              -> BB2   else -> BB5
BB2  load+cmp: x = a[i];  c = x > threshold
               if (c)                  -> BB3   else -> BB4
BB3  MAC:      y = b[i];  p = x*y;  acc = acc + p   -> BB4
BB4  incr:     i = i + 1                         -> BB1   (loop back-edge)
BB5  store:    *result = acc;  return

The control-flow graph (CFG)

Now there is real control flow, so the CFG matters — it records which basic blocks execute and in what order; its edges are the branches and the loop back-edge.

Vocabulary you now own — basic block, branch, loop back-edge, control dependence, data dependence, live variable. HLS turns the CFG into the controller (FSM).

Stage B schedule — one loop iteration

Assume: 1 memory port, load = 1 cycle, compare = 1, non-pipelined multiply = 3, add = 1. The schedule is non-speculative — b[i] is loaded only after the compare resolves the branch, matching the FSM below.

Taken path (x > threshold):

Cycle Operation
1 load a[i] → x
2 compare x > threshold → branch resolves
3 load b[i] → y
4–6 multiply p = x*y
7 accumulate acc = acc + p
8 i++, loop check

Not-taken path: load, compare, i++ → 3 cycles.

Two things fall out of this schedule: variable latency per iteration (it depends on the data), and the loop-carried dependence on acc — the next iteration's accumulate waits on this one. We leave it un-pipelined here; that loop-carried dependence is exactly what L2's pipeline and L3's breakdown are about.

Part V — RTL generation: three components

The schedule + CFG lower to RTL with three principal components:

  1. Datapath — adders, multipliers, comparators, muxes, registers.
  2. Controller (FSM) — decides which operations occur each cycle.
  3. Memory / interface logic — address generators, RAM ports, handshaking. (Called out as first-class because memory architecture is the recurring performance theme of L4–L5.)

The FSM for Stage B

Basic blocks do not become RTL modules directly. Operations are scheduled into clock cycles, and the schedule is realized as a datapath controlled by an FSM, talking to memory through an interface.

Part VI — Software vs hardware, and the whole flow

Contrast. For software, five instructions (load, compare, branch, multiply, add) reuse the processor's one datapath over time. For synthesized hardware, a load unit + comparator + multiplier + adder + registers + controller persist and operate every clock cycle.

In software, the program moves through the processor. In hardware synthesis, the compiler builds a processor-like structure around the program — an application-specific datapath, not a general-purpose processor.

The whole flow, end to end — and it marks where the rest of the course operates:

   C/C++ program
        │  parse
   Compiler IR
        │
   CFG  +  DFG
        │  dependence analysis
   Scheduling                <-- L1 ends here (mechanism understood)
        │
   Allocation + Binding
        │
   Datapath + Controller + Memory interface
        │
   RTL
        │  synthesis, place & route
   FPGA bitstream            <-- L2 makes this concrete + runs it on the U50

The one message to take away. HLS is not a C-to-Verilog translator. It is a compiler-driven process of choosing a hardware architecture for a computation — and the choices it makes are what we spend the rest of the course learning to control.

Looking ahead: a GEMM kernel goes from 25074 ms → 112 ms (223×) with the right restructuring. By L6 you'll understand every number.
