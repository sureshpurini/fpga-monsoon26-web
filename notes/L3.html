Lecture 3 — Why "just add pragmas" fails

Student handout · FPGA-based Accelerator Design · Monsoon 2026

Scope. Lecture 2 ended with a cliffhanger: change one word — an accumulator from int to float — and the very same #pragma HLS PIPELINE II=1 quietly stops delivering. This lecture explains why, precisely, and how to earn II = 1 back. We build the idea of a recurrence up slowly (what a dependency is, why it forms a feedback loop, and the one inequality that falls out), meet a second, independent way II is forced above 1 (a structural / memory-port hazard), separate PIPELINE from UNROLL, and close on fixed-point as the FPGA's home turf. Everything is measured on our U50 (Vitis 2025.1), cosim-verified — and it all lives on a single dot product, the kernel the next lecture scales into GEMM. This handout follows the Lecture 3 slides.

Thesis (the spine). A pragma is a request, not a guarantee. The II you actually get is the maximum of three things: what you asked for, what the recurrence allows (a data hazard), and what the resources allow (a structural hazard). "Just add PIPELINE" moves only the first. Performance on a real loop is something you earn — by moving a bound you can write down — not something a directive grants.

Learning outcomes

By the end of this lecture you can:

  1. Define a loop-carried dependency and a recurrence, and point to the cycle they form in a dataflow graph.
  2. State and apply the recurrence bound $\text{II} \ge \lceil L/d \rceil$, and explain why the pragma and the multiply are not in it.
  3. Read Target vs achieved II off a synthesis report and diagnose the cause from the HLS log (carried dependence ⇒ data hazard; limited memory ports ⇒ structural hazard).
  4. Distinguish a data hazard (recurrence) from a structural hazard (port), and write achieved II as a max of three bounds.
  5. Break a recurrence two ways — raise the distance $d$ (interleaved partial sums / tree reduction) or lower the latency $L$ (fixed-point) — and earn II = 1.
  6. Contrast PIPELINE (temporal, one datapath) with UNROLL (spatial, many datapaths); compute throughput $U/\text{II}$; and explain why unrolling alone does not break a recurrence.
  7. Use ap_int / ap_fixed deliberately, and explain fixed-point's double win: a shorter recurrence and a higher compute roof.

Running example — one word changed

The whole lecture turns on a single loop, and a single edit to it. On the left, the happy path from Lecture 2; on the right, the one-word change that breaks it:

int acc = 0;                 float acc = 0;         // one word changed
for (i) {                    for (i) {
#pragma HLS PIPELINE II=1    #pragma HLS PIPELINE II=1
  acc += a[i]*b[i];            acc += a[i]*b[i];
}                            }
// II = 1: 1-cycle add       // II = ? : multi-cycle add feeds itself

Same pragma, one word different — and the achieved II flips. To see why, we build the idea up from first principles.

Part I — The recurrence, precisely

Step 1 — does iteration i+1 need iteration i?

A loop-carried dependency is a value written in one iteration and read in a later one. vadd has none — every output is independent, which is exactly why it pipelined freely in Lecture 2. acc += a[i]*b[i] has one, on acc: iteration i+1 reads the acc that iteration i wrote. Everything hard in this lecture traces to that single edge.

Step 2 — a loop-carried dependency is a feedback loop

Draw it in the dataflow and the dependency becomes a cycle: the adder's output acc feeds back into the adder's own input, + → acc → +. A recurrence is a loop-carried dependency whose path runs through one or more operators, closing such a cycle. Crucially, the multiply sits off the cycle — its output feeds the adder but nothing feeds back into it — so it lengthens latency, never II.

Step 3 — two numbers describe every recurrence

  • Latency $L$ — the number of cycles for the operator(s) on the cycle to produce the fed-back value. An integer add has $L = 1$; a float add has $L = 3$ (measured on this fabric).
  • Distance $d$ — how many iterations apart the write and the read are. For acc += a[i]*b[i], iteration i writes and i+1 reads, so $d = 1$.

$L$ is how long the value takes to come back; $d$ is how long until it is needed again. The whole question is which is bigger.

Step 4 — why the recurrence caps II

If the fed-back value takes $L$ cycles to return but is needed every $d$ iterations, then a new iteration can begin only once every $\lceil L/d \rceil$ cycles — otherwise it would reach for an acc that does not exist yet.

The recurrence bound — the one inequality

$$\text{II} \;\ge\; \left\lceil \frac{L}{d} \right\rceil$$

The ceiling is there because II is a whole number of cycles. Two things are not in this formula: the pragma (so asking for II=1 changes nothing here) and the multiply (it is off the cycle). Only operators on the loop-carried cycle set this floor. If $L/d > 1$ you cannot have II = 1 — until you change $L$ or $d$ (Part II).

Apply it — integer vs float

  • Integer accumulate: $L = 1$, $d = 1 \Rightarrow \text{II} = \lceil 1/1 \rceil = 1$. The 1-cycle add closes the loop in one cycle, so a new iteration starts every clock.

  • Float accumulate: $L = 3$, $d = 1 \Rightarrow \text{II} = \lceil 3/1 \rceil = 3$. The multi-cycle float add cannot feed the next iteration in time, so the adder idles two cycles out of three.

Measured — the tool names the cause, verbatim

Synthesize the float version (U50, Vitis 2025.1) and read the HLS log:

[HLS 200-880]  Unable to enforce a carried dependence constraint
               (II = 1, distance = 1, offset = 0) ... on 'acc'.
[HLS 200-1470] Pipelining result : Target II = 1, Final II = 3, loop 'prod'

Target II = 1, Final II = 3. The pragma asked; the tool relaxed it and named the cause — a carried dependence on acc, distance 1. The habit to build now: read the achieved II, not the requested one.

Which carried dependencies actually cost II?

Not every carried dependency is a recurrence. Only one whose path forms a cycle taxes II; a value that is merely carried forward (written late, read even later, with no feedback) never does.

The same point, from the operator's side: a slow operator placed off a cycle only adds depth — the pipe fills once and then a new iteration issues every clock, so II stays 1.

Put the same slow operator on a feedback cycle and its latency becomes the II:

A second, independent bound — the structural hazard

The recurrence is one way II is forced above 1. Here is a second, which needs no dependency at all:

// a 4-tap sum: FOUR reads of x[] per output, through ONE memory port
for (int i = 0; i < N; i++) {
#pragma HLS PIPELINE II=1
  y[i] = x[i] + x[i+1] + x[i+2] + x[i+3];   // 4 loads of x, 1 port
}

Each y[i] is independent — by the recurrence bound alone, II = 1. But the four reads of x must share one memory port, so at most one is served per cycle: $\text{II} \ge \lceil \text{uses}/\text{ports} \rceil = \lceil 4/1 \rceil = 4$. A structural hazard: the port, not a dependency, sets II.

Give x more ports or banks and the bound falls — $\lceil 4/2 \rceil = 2$, then 1. That is banking, and it is the subject of a later lecture.

Achieved II is a max of three bounds

$$\text{II}\text{achieved} = \max\big(\ \text{requested},\ \underbrace{\lceil L/d\rceil}\ \big)$$}},\ \underbrace{\lceil \text{uses}/\text{ports}\rceil}_{\text{resource}

Bound equals Hazard (familiar from CPU pipelines)
requested the II=n you asked for —
recurrence (RecMII) $\lceil L/d \rceil$ over feedback cycles data hazard
resource (ResMII) $\lceil \text{uses}/(\text{ports}\cdot\text{units}) \rceil$ per iteration structural hazard

"Just add PIPELINE" moves only the requested row. You have now seen both others — the acc recurrence (data) and the 4-tap port clash (structural). Both reappear on a real kernel, GEMM, in the next lecture.

(For the curious — one operator on a cycle gives $\lceil L/d \rceil$; a cycle through several operators generalizes to the iteration bound $\text{RecMII} = \max_{\text{cycle } c} \lceil \sum_c \text{latency} / \sum_c \text{distance} \rceil$. In DSP hardware this is Parhi's "iteration bound"; in compilers it is the RecMII of modulo scheduling (Rau 1994; Lam, PLDI 1988). HLS loop pipelining is software pipelining, realized in hardware; Vitis solves it with SDC scheduling (Cong & Zhang, DAC 2006).)

Read it off the report

Report field Tells you
Target II what the pragma asked for
Final / achieved II the truth — this is your throughput
Iteration Latency ramp cost (includes the multiply)
Loop Latency $\approx$ IterLat $+ (\text{Trip} - 1)\cdot\text{II}$

The report gives the number; the HLS log gives the cause — carried dependence means a data hazard, limited memory ports means a structural one. Diagnosing from both is the core lab skill.

Part II — Breaking the recurrence

The bound $\text{II} \ge \lceil L/d \rceil$ is a floor you can move, and it names its own two levers:

  • Lever 1 — raise the distance $d$: reuse each accumulator less often (interleaved partial sums), or reassociate the sum into a tree. Costs registers / adders.
  • Lever 2 — lower the latency $L$: make the feedback operator faster — drop to fixed-point. Costs precision.

Everything else is a special case. Nothing is free — you pay in area or in bits.

Lever 1 — interleaved partial sums

float acc[P] = {0};
#pragma HLS ARRAY_PARTITION variable=acc complete   // P separate registers
for (i) {
#pragma HLS PIPELINE II=1
  acc[i % P] += a[i]*b[i];        // each lane touched every P iterations → d = P
}
float sum = 0; for (p) sum += acc[p];   // one-time reduction at the end

Each accumulator is now touched only every $P$ iterations, so its distance is $P$ and $\text{II} \ge \lceil L/P \rceil$. Choose $P \ge L$ and II = 1 — on the same float type. The lab partial-sums ($P = 8$) measures II = 1.

Lever 1b — tree reduction (reassociate)

The products are independent; only the sum was serial. Reassociating a chain of adds into a balanced tree shortens the critical path from $N\cdot L$ to $\log_2 N \cdot L$.

One caution: float addition is not associative, so HLS will not reorder it for you — you restructure it explicitly (partial sums), or grant fast-math permission. Integer and ap_fixed reassociate for free.

Lever 2 — lower the latency: fixed-point

typedef ap_fixed<32,10> acc_t;   // 1-cycle add — the recurrence closes immediately
acc_t acc = 0;
for (i) {
#pragma HLS PIPELINE II=1
  acc += a[i]*b[i];              // same pragma, no interleaving
}

With $L = 1$, $\text{II} = \lceil 1/1 \rceil = 1$ — the cheapest fix when it is numerically acceptable, with no extra adders. The lab fixed-pipe-k measures II = 1.

The design space on one page

Fix Lever II Cost
do nothing (float) — 3 throughput lost
partial sums ($P \ge L$) ↑ distance 1 $P$ adders + registers; changed rounding
tree reduction ↑ distance 1 adders; float needs permission
fixed-point accumulator ↓ latency 1 precision / range design

There is nothing magic about II = 1 — you earn it by attacking $L$ or $d$ in a formula you can write down.

Part III — PIPELINE vs UNROLL

These are the two knobs, and students routinely conflate them. PIPELINE overlaps iterations on one datapath (the knob is II, a temporal change — it alters the schedule). UNROLL makes U copies that run at once (the knob is U, a spatial change — it alters the layout).

The same loop can be built four ways — baseline, pipelined, unrolled, and pipelined-and-unrolled — differing only in how densely results retire (time) and how many datapaths pay for it (space):

The single formula that ties them together is throughput = $U/\text{II}$:

Build Area II Cycles (N=1000) results/cyc
baseline 1 4 ~4000 ¼
PIPELINE II=1 1 1 ~1003 1
UNROLL 4 4 4 ~1000 1
UNROLL 4 + PIPELINE 4 1 ~253 4

$$\text{results / cycle} = \frac{U}{\text{II}}, \qquad \text{cycles} \approx L + \Big(\tfrac{N}{U} - 1\Big)\cdot\text{II}$$

There are two routes to one-result-per-cycle: pipelining pays in registers, unrolling pays in 4× area. The rule of thumb: pipeline first (cheap), then unroll to push past one per cycle. And you rarely write UNROLL yourself — pipelining a loop auto-unrolls any inner compile-time loop to fill it, which is exactly the mechanism that misfires on GEMM in the next lecture.

The trap — UNROLL does not break a recurrence

// UNROLL 4 on a float accumulate, no reassociation:
acc = acc + p0;  acc = acc + p1;  acc = acc + p2;  acc = acc + p3;   // one serial chain, 4·L

Unrolling handed you four adders — but they are chained, not parallel: a length-$4L$ path that still feeds acc back to itself. $U$ rose, but so did II, so $U/\text{II}$ does not improve. Unrolling multiplies throughput only for independent iterations; a reduction needs its independence manufactured first (partial sums or a tree, Part II). Unroll gives the adders; partial sums give the independence that lets them run in parallel.

Where it stops paying — the ceiling on U

  • Area grows with $U$ (LUT · FF · DSP). The U50 has 5,952 DSPs; a float FMA costs ≈ 5, an integer / fixed MAC ≈ 1.
  • The bounds cap $U$: you cannot out-unroll a recurrence, and unrolling raises the memory uses per cycle — so the structural bound bites (too many reads, one port).
  • The roofline caps $U$: past the compute or memory roof, extra datapaths sit idle.

First remove the recurrence, then spend area — in that order. The next lecture shows, measured, what happens when you unroll a loop whose operands share one memory port: area explodes for zero throughput.

Part IV — Fixed vs floating point

Fixed-point is the FPGA's home turf, and the ap_ types make precision a knob you set rather than a language default.

  • ap_int<W> / ap_uint<W> — arbitrary-width integers ($W \approx 1 \ldots 1024$). Use the bits the data needs: a 12-bit sample is ap_uint<12>, not int.
  • ap_fixed<W,I> — $W$ total bits, $I$ integer and $W-I$ fractional. Integer hardware underneath means a 1-cycle add. Rounding (AP_RND) and overflow (AP_SAT) become your explicit choices.

Fixed-point wins twice

  1. A shorter recurrence — a 1-cycle add gives II = 1 with no interleaving (Part II).
  2. A higher compute roof — 1 DSP is one integer/fixed MAC, but a float FMA costs ≈ 5 DSPs, and INT8 packs two MACs per DSP. On the same silicon that is roughly ~3.6 TOP/s (integer MAC) or ~7.1 TOP/s (INT8) against ~0.71 TFLOP/s (FP32) — a 5–10× headroom.

This is why the FPGA loves low precision — the opening claim of Lecture 1, now cashed.

The cost — and when float still wins

You design the range ($I$ bits) and the precision ($W-I$ bits), then verify against a floating-point reference with a tolerance (our testbench does exactly this, and passes). When the dynamic range is huge or unknown, float earns its keep. The lesson is not "always fixed" — it is choose precision on purpose.

Where this goes next — scale the dot product to GEMM

You can now earn II = 1 on a real reduction: the pragma is a request; you move the recurrence (raise $d$ or lower $L$) and read the structural (uses / ports) bound. But one dot product is not a kernel. Wrap it in the two loops that walk every output — matrix multiply — and both walls get real at once: the same acc recurrence, and a memory-port wall that no recurrence fix can touch. The next lecture builds GEMM from formulation to measured FPGA analysis, where which loop you pragma decides which hazard you hit — and a change of dataflow finally earns II = 1 back at scale.
