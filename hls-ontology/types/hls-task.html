hls::task / hls_thread_local

Types for data-driven task-level parallelism. Tasks execute based on data availability rather than control flow.

Header

#include <hls_task.h>

hls::task

Creates a concurrent task that runs when input data is available.

Syntax

hls_thread_local hls::task t(function, stream_args...);
Parameter Description
function Function to execute as task body
stream_args hls::stream arguments connecting tasks

Characteristics

  • Tasks start automatically when input data available
  • Tasks run continuously (no explicit loop needed)
  • Communication via hls::stream only
  • Must be declared with hls_thread_local

hls_thread_local

Storage specifier for data-driven TLP. Marks variables as persistent across invocations.

Syntax

hls_thread_local hls::stream<T> stream("name");
hls_thread_local hls::task t(func, args...);

Required For

  • All internal hls::stream in data-driven designs
  • All hls::task declarations
  • Internal FIFOs between tasks

Understanding hls_thread_local

Why It's Needed

In data-driven TLP, tasks run infinitely - the top function may be called repeatedly, but tasks and internal streams must persist between calls. Without hls_thread_local, streams would be recreated fresh each call, losing all buffered data.

void top(hls::stream<int>& in, hls::stream<int>& out) {
    // WITHOUT hls_thread_local: recreated every call = BROKEN
    hls::stream<int> s1;        // New stream each call - data lost!
    hls::task t1(func, s1);     // New task each call - broken!

    // WITH hls_thread_local: persists across calls = CORRECT
    hls_thread_local hls::stream<int> s1;  // Same stream persists
    hls_thread_local hls::task t1(func, s1); // Same task continues
}

Execution Model

  1. Host calls top() function
  2. First call: streams and tasks are CREATED
  3. Tasks begin running, processing data from streams
  4. top() returns, but streams/tasks PERSIST (due to hls_thread_local)
  5. Host calls top() again - same streams/tasks continue
  6. Data flows through persistent pipeline across calls

What Needs hls_thread_local?

Item Needs it? Why
Internal hls::stream YES Must persist data between top-level calls
hls::task declarations YES Task must continue running across calls
hls::stream<T, DEPTH> YES Same as regular stream - internal FIFO
Top-level stream parameters NO Passed in from outside, not created internally
Local vars in task functions NO Task function itself is the persistent unit
Regular local variables NO Recreated per invocation is fine for temps

Static Variable Analogy

Think of hls_thread_local like C++ static variables:

// Regular C++ - static persists across function calls
void counter() {
    static int count = 0;  // Persists
    count++;
}

// HLS - hls_thread_local persists across top-level calls
void top(...) {
    hls_thread_local hls::stream<int> s;  // Persists
    hls_thread_local hls::task t(func, s); // Persists
}

Example Breakdown

void odds_and_evens(hls::stream<int>& in,    // NO - parameter
                    hls::stream<int>& out1,   // NO - parameter
                    hls::stream<int>& out2) { // NO - parameter

    // YES - internal streams need hls_thread_local
    hls_thread_local hls::stream<int, 5> s1;
    hls_thread_local hls::stream<int, 5> s2;

    // YES - all tasks need hls_thread_local
    hls_thread_local hls::task t1(splitter, in, s1, s2);
    hls_thread_local hls::task t2(odds, s1, out1);
    hls_thread_local hls::task t3(evens, s2, out2);
}

Common Error

Forgetting hls_thread_local causes synthesis errors:

ERROR: [HLS 214-178] hls::task object must be declared with hls_thread_local

Solution: Add hls_thread_local before ALL internal streams and tasks.

Stream Depth Template Parameter

Streams can specify depth as a template parameter (shorthand for #pragma HLS STREAM depth=):

// Syntax: hls::stream<T, DEPTH>
hls_thread_local hls::stream<int, 16> buffered_stream;  // depth=16

// Equivalent to:
hls_thread_local hls::stream<int> buffered_stream;
#pragma HLS STREAM variable=buffered_stream depth=16

Depth sizing guidance: - Minimum: N / num_consumers for balanced distribution - Increase for: unbalanced data, variable processing times - Default depth is 2 if unspecified

Basic Example

#include <hls_task.h>
#include <hls_stream.h>

// Task functions - no explicit loops needed
void producer(hls::stream<int>& out) {
    static int counter = 0;
    out.write(counter++);
}

void doubler(hls::stream<int>& in, hls::stream<int>& out) {
    int val = in.read();
    out.write(val * 2);
}

void consumer(hls::stream<int>& in, hls::stream<int>& result) {
    int val = in.read();
    result.write(val);
}

void top(hls::stream<int>& output) {
    // All streams must be hls_thread_local
    hls_thread_local hls::stream<int> c1("c1");
    hls_thread_local hls::stream<int> c2("c2");

    // All tasks must be hls_thread_local
    hls_thread_local hls::task t1(producer, c1);
    hls_thread_local hls::task t2(doubler, c1, c2);
    hls_thread_local hls::task t3(consumer, c2, output);
}

Diamond Pattern (Data-Driven)

#include <hls_task.h>
#include <hls_stream.h>

void funcA(hls::stream<int>& in,
           hls::stream<int>& out1,
           hls::stream<int>& out2) {
    int val = in.read();
    out1.write(val);
    out2.write(val);
}

void funcB(hls::stream<int>& in, hls::stream<int>& out) {
    int val = in.read();
    out.write(val * 2);
}

void funcC(hls::stream<int>& in, hls::stream<int>& out) {
    int val = in.read();
    out.write(val + 10);
}

void funcD(hls::stream<int>& in1,
           hls::stream<int>& in2,
           hls::stream<int>& out) {
    int v1 = in1.read();
    int v2 = in2.read();
    out.write(v1 + v2);
}

void top(hls::stream<int>& in, hls::stream<int>& out) {
    hls_thread_local hls::stream<int> c1("c1"), c2("c2"), c3("c3"), c4("c4");

    hls_thread_local hls::task t1(funcA, in, c1, c2);
    hls_thread_local hls::task t2(funcB, c1, c3);
    hls_thread_local hls::task t3(funcC, c2, c4);
    hls_thread_local hls::task t4(funcD, c3, c4, out);
}

Splitter Pattern (Conditional Routing)

Routes data to different outputs based on data values. Unlike fork (which duplicates), splitter sends each element to exactly ONE path.

#include "hls_task.h"

#define N 10

// Splitter: routes based on condition (odd vs even)
void splitter(hls::stream<int>& in,
              hls::stream<int>& odds_buf,
              hls::stream<int>& evens_buf) {
    int data = in.read();
    if (data % 2 == 0)
        evens_buf.write(data);
    else
        odds_buf.write(data);
}

void odds(hls::stream<int>& in, hls::stream<int>& out) {
    out.write(in.read() + 1);
}

void evens(hls::stream<int>& in, hls::stream<int>& out) {
    out.write(in.read() + 2);
}

void odds_and_evens(hls::stream<int>& in,
                    hls::stream<int>& out1,
                    hls::stream<int>& out2) {
    // Stream depth = N/2 for balanced 2-way split
    hls_thread_local hls::stream<int, N / 2> s1;
    hls_thread_local hls::stream<int, N / 2> s2;

    hls_thread_local hls::task t1(splitter, in, s1, s2);
    hls_thread_local hls::task t2(odds, s1, out1);
    hls_thread_local hls::task t3(evens, s2, out2);
}

Key points: - Splitter writes to exactly ONE output per input read - Stream depth sized for expected distribution (N/2 for balanced split) - See data-driven-splitter pattern for full details

Task Arrays

Create multiple parallel tasks using an array with #pragma HLS unroll.

#include "hls_np_channel.h"  // For hls::split and hls::merge
#include "hls_task.h"

const int NP = 4;  // Number of parallel workers

void worker(hls::stream<int>& in, hls::stream<int>& out) {
    int i = in.read();
    out.write(i * 2 + 1);
}

void dut(int in[N], int out[N], int n) {
    // Split distributes input round-robin to NP outputs
    hls_thread_local hls::split::round_robin<int, NP> split1;
    // Merge collects from NP inputs round-robin
    hls_thread_local hls::merge::round_robin<int, NP> merge1;

#pragma HLS dataflow

    read_in(in, n, split1.in);

    // Task array - creates NP parallel workers
    hls_thread_local hls::task t[NP];
    for (int i = 0; i < NP; i++) {
#pragma HLS unroll  // REQUIRED - expands to NP separate task instantiations
        t[i](worker, split1.out[i], merge1.in[i]);
    }

    write_out(merge1.out, out, n);
}

Key points: - #pragma HLS unroll is required - without it, tasks aren't properly instantiated - Combines control-driven (#pragma HLS dataflow) with data-driven (hls::task) - Use hls::split for fan-out and hls::merge for fan-in - See merge-split pattern for split/merge details

Template Uniquification

Problem: hls::task is persistent - calling a function with tasks multiple times reuses the SAME tasks!

void process(streams...) {
    hls_thread_local hls::task t(func, ...);  // Persistent!
}

void bad_top() {
    process(in1, out1);  // Creates task t
    process(in2, out2);  // REUSES same task t - likely wrong!
}

Solution: Use a dummy template parameter to create unique instantiations.

template <typename>  // Dummy type parameter - never actually used
void reusable_module(hls::stream<int>& in, hls::stream<int>& out) {
#pragma HLS dataflow
    hls_thread_local hls::stream<int> internal;
    hls_thread_local hls::task t(func, in, internal);
    // Each template instantiation gets its OWN streams and tasks
}

void good_top() {
    reusable_module<class c1>(in1, out1);  // Unique instance 1
    reusable_module<class c2>(in2, out2);  // Unique instance 2 (separate tasks!)
}

How it works: - template <typename> creates a function template - class c1, class c2 are forward-declared dummy classes - reusable_module<class c1> and reusable_module<class c2> are different functions - Each function gets its own hls_thread_local variables

When to use: - Calling same dataflow function multiple times with different streams - Creating reusable "dataflow modules" containing tasks - Building composable task-based designs

Data-Driven vs Control-Driven

Aspect Data-Driven (hls::task) Control-Driven (#pragma HLS DATAFLOW)
Execution trigger Data availability Control flow
Loop structure Implicit (continuous) Explicit loops
Keyword hls_thread_local hls::task #pragma HLS DATAFLOW
Best for Variable data rates Fixed iteration counts

Control-Driven Equivalent

// Control-driven version (for comparison)
void top_control_driven(int* in, int* out, int n) {
#pragma HLS DATAFLOW
    hls::stream<int> c1, c2;

    // Explicit loops required
    for (int i = 0; i < n; i++) producer(c1, in[i]);
    for (int i = 0; i < n; i++) process(c1, c2);
    for (int i = 0; i < n; i++) consumer(c2, out[i]);
}

When to Use

Use Case Recommendation
Variable data rates Data-driven (hls::task)
Continuous streaming Data-driven (hls::task)
Fixed iteration counts Control-driven (DATAFLOW pragma)
Simpler designs Control-driven (DATAFLOW pragma)

Common Pitfalls

Pitfall Solution
Forgetting hls_thread_local Always use for streams and tasks
Explicit loops in task functions Remove loops - tasks run continuously
Using with DATAFLOW pragma Choose one model, not both
Non-stream arguments All task args must be hls::stream
Unbalanced stream reads Each task must read same count as upstream writes
Reusing task functions Use template uniquification (see above)
Task array without unroll Add #pragma HLS unroll in initialization loop

Deadlock Pitfalls

Stream Balance Rule

Each task invocation must consume exactly as many elements as upstream produces per invocation.

Violating this rule causes deadlock - a task blocks forever waiting for data that never arrives.

Problem Code (Deadlock)

// WRONG - reads twice but upstream only writes once per invocation
void func3(hls::stream<int>& in, hls::stream<int>& out) {
    int c = in.read();   // 1st read - OK
    c = in.read();       // 2nd read - DEADLOCK! Upstream only sent 1 element
    out.write(c);
}

Fixed Code

// CORRECT - balanced reads/writes
void func3(hls::stream<int>& in, hls::stream<int>& out) {
    int c = in.read();   // 1 read matches upstream's 1 write
    out.write(c);
}

Debugging Deadlocks

  1. Run C Simulation with "Launch Debugger" option in Vitis HLS
  2. Click Resume - see "deadlock detected when simulating hls::tasks"
  3. In Debug window, examine Suspended threads
  4. Look for tasks blocked on stream.read()
  5. Check read/write counts match across the pipeline
