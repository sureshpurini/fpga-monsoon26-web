Data-Driven Splitter Pattern

Conditional data routing using hls::task for data-driven task-level parallelism. Routes each data element to exactly one output path based on a runtime condition.

Overview

Unlike fork patterns that duplicate data to all paths, the splitter pattern examines each element and sends it to exactly ONE output based on a condition. Uses hls::task for persistent, infinitely-running task instances.

            ┌─→ path_a_buf ─→ process_a() ─→ out_a  (condition true)
in ─→ splitter()
            └─→ path_b_buf ─→ process_b() ─→ out_b  (condition false)

Key Constructs

Construct Purpose
hls::task Creates persistent task running infinitely
hls_thread_local Storage class for task/stream persistence
hls::stream<T, DEPTH> FIFO with explicit depth as template parameter

Syntax

// Stream with depth template parameter
hls_thread_local hls::stream<T, DEPTH> stream_name;

// Task declaration
hls_thread_local hls::task task_name(function, stream_args...);
Parameter Type Description
T type Data type to stream
DEPTH int FIFO depth (elements)
function func Task body function
stream_args streams Input/output streams

Complete Example

From Vitis-HLS-Introductory-Examples/.../simple_data_driven/test.cpp:

#include "hls_task.h"

#define N 10

// Splitter: routes odd/even numbers to different paths
void splitter(hls::stream<int>& in, hls::stream<int>& odds_buf,
              hls::stream<int>& evens_buf) {
    int data = in.read();
    if (data % 2 == 0)
        evens_buf.write(data);
    else
        odds_buf.write(data);
}

// Process odd numbers: add 1
void odds(hls::stream<int>& in, hls::stream<int>& out) {
    out.write(in.read() + 1);
}

// Process even numbers: add 2
void evens(hls::stream<int>& in, hls::stream<int>& out) {
    out.write(in.read() + 2);
}

// Top function with data-driven tasks
void odds_and_evens(hls::stream<int>& in, hls::stream<int>& out1,
                    hls::stream<int>& out2) {
    // Internal streams - MUST be hls_thread_local
    hls_thread_local hls::stream<int, N / 2> s1; // odds buffer
    hls_thread_local hls::stream<int, N / 2> s2; // evens buffer

    // Tasks - MUST be hls_thread_local
    hls_thread_local hls::task t1(splitter, in, s1, s2);
    hls_thread_local hls::task t2(odds, s1, out1);
    hls_thread_local hls::task t3(evens, s2, out2);
}

Code Generation Guidelines

Kernel Template

#include "hls_task.h"

void splitter(hls::stream<T>& in,
              hls::stream<T>& out_a,
              hls::stream<T>& out_b) {
    T data = in.read();
    if (CONDITION(data))
        out_a.write(data);
    else
        out_b.write(data);
}

void process_a(hls::stream<T>& in, hls::stream<T>& out) {
    out.write(TRANSFORM_A(in.read()));
}

void process_b(hls::stream<T>& in, hls::stream<T>& out) {
    out.write(TRANSFORM_B(in.read()));
}

void top(hls::stream<T>& in,
         hls::stream<T>& out_a,
         hls::stream<T>& out_b) {
    hls_thread_local hls::stream<T, DEPTH> buf_a;
    hls_thread_local hls::stream<T, DEPTH> buf_b;

    hls_thread_local hls::task t1(splitter, in, buf_a, buf_b);
    hls_thread_local hls::task t2(process_a, buf_a, out_a);
    hls_thread_local hls::task t3(process_b, buf_b, out_b);
}

Task Function Template

// Task functions run infinitely - NO explicit loop needed
void task_func(hls::stream<T>& in, hls::stream<T>& out) {
    // Single iteration - task framework handles repetition
    T data = in.read();   // Blocking read
    T result = process(data);
    out.write(result);    // Blocking write
}

Key Constraints

Constraint Requirement
Storage class All hls::stream and hls::task MUST use hls_thread_local
Task functions No explicit loops - run infinitely by framework
Communication Only via hls::stream (no shared memory between tasks)
Splitter output Must write to exactly ONE output per input read

Required Pragmas

Pragma Required? Purpose
None - Data-driven TLP uses hls::task, not pragmas

Test Bench Generation Guidelines

Test Bench Template

#include "test.h"

int main() {
    // 1. Declare streams with appropriate depths
    hls::stream<int, N> in;
    hls::stream<int, N / 2> out1;  // For path A
    hls::stream<int, N / 2> out2;  // For path B

    // 2. Feed input data
    for (int i = 0; i < N; i++)
        in.write(i);

    // 3. Execute DUT
    odds_and_evens(in, out1, out2);

    // 4. Verify outputs
    int sum1 = 0, sum2 = 0;
    for (int i = 0; i < N / 2; i++)
        sum1 += out1.read();
    for (int i = 0; i < N / 2; i++)
        sum2 += out2.read();

    // 5. Check expected results
    // Odds (1,3,5,7,9) + 1 each = 2+4+6+8+10 = 30
    // Evens (0,2,4,6,8) + 2 each = 2+4+6+8+10 = 30
    if ((sum1 != 30) && (sum2 != 30))
        return 1;  // FAIL

    return 0;  // PASS
}

Stream Interface Notes

// For data-driven TLP, use hls::stream for all I/O

    input_stream.write(test_data[i]);

Verification Methods

Method When to Use
Sum verification When order varies but total is predictable
Count verification When distribution is known
Element-by-element When order is deterministic

Optimization Guidance for Agents

When to Apply This Pattern

Decision tree:
├── Need to route data to different paths based on value?
│   ├── Yes → Continue
│   └── No → Use fork pattern (dataflow-diamond)
├── Data rate varies per path?
│   ├── Yes → Data-driven splitter (this pattern)
│   └── No → Control-driven DATAFLOW may suffice
├── Paths have different processing times?
│   └── Yes → Increase stream depth for slower path

Performance Optimization

Optimization How to Apply Expected Impact
Stream depth Increase DEPTH in hls::stream<T, DEPTH> Prevents stalls from imbalanced distribution
Task pipelining Add #pragma HLS PIPELINE II=1 inside task functions Improves throughput per task
Wider data Use hls::vector<T, N> as stream type Higher bandwidth

Resource vs Performance Trade-offs

Choice Performance Impact Resource Impact
Small stream depth May stall on imbalanced data Fewer BRAMs
Large stream depth Absorbs data bursts More BRAMs
More parallel paths Higher throughput More logic per path

Parameter Tuning

Parameter Low Value High Value Guidance
Stream DEPTH Stalls on bursts Absorbs imbalance Start with N/num_paths, increase if stalls
Num paths Simpler logic Higher parallelism Match natural data categories

Common Pitfalls

Pitfall Symptom Solution
Missing hls_thread_local Synthesis error Add to ALL streams and tasks
Explicit loops in task Task runs once then stops Remove loops - framework handles repetition
Shared memory between tasks Race conditions Use only hls::stream for communication
Unbalanced stream depth Deadlock or stalls Size depth for worst-case imbalance
Splitter writes to multiple outputs Data duplication Write to exactly ONE output per input
Unbalanced stream reads Deadlock Each task must read same count as upstream writes
Reusing task functions Shared tasks/streams Use template uniquification
Task array without unroll Tasks not instantiated Add #pragma HLS unroll

Data-Driven vs Control-Driven

Aspect Data-Driven (hls::task) Control-Driven (#pragma HLS DATAFLOW)
Execution trigger Data availability Control flow
Loop structure Implicit (continuous) Explicit loops required
Keyword hls_thread_local hls::task #pragma HLS DATAFLOW
Best for Variable data rates, conditional routing Fixed iteration counts

Related Patterns

  • merge-split - Round-robin or load-balanced distribution
