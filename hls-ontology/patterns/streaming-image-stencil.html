Streaming Image Stencil Pattern

Process a 2D image with a sliding K×K window as a true streaming dataflow pipeline: each pixel flows through stages connected by hls::stream FIFOs, with on-chip line buffers caching the rows needed for the window. This is the canonical HLS pattern for image-processing kernels that target one pixel per cycle (II=1) with minimal BRAM footprint.

Use this whenever a kernel reads a 2D image, applies a fixed-radius neighborhood operation, and writes a 2D image — regardless of whether the operation is smoothing, gradient, non-maximum suppression, thresholding, or anything else.

Overview

The streaming-stencil architecture has three distinct concerns, each isolated in its own function:

img_inp ─► read_padded ─stream─► stencil_stage ─stream─► write_cropped ─► img_out
   (m_axi)      │                      │                      │             (m_axi)
                │                      │                      │
            raster read           K-tap window               raster write
            with padding          + line buffer              with cropping

For multi-pass pipelines (e.g., smoothing → gradient → suppression → thresholding), chain N stencil_stage functions through additional hls::stream channels under one top-level #pragma HLS DATAFLOW. Each stage has its own line buffer and window — none of them materialize a full intermediate image.

Key Constructs

Construct Purpose
#pragma HLS DATAFLOW Run all stages concurrently with FIFO connections
hls::stream<T> Inter-stage FIFO channels — never materialize full images between stages
Line buffer lb[K-1][MAX_W] Cache the K−1 most-recently-read rows on chip
Window w[K][K] Hold the current K×K neighborhood as scalar registers
#pragma HLS ARRAY_PARTITION variable=lb complete dim=1 All line buffer rows readable in the same cycle
#pragma HLS ARRAY_PARTITION variable=w complete dim=0 All K² window cells live in registers, not BRAM
#pragma HLS DEPENDENCE variable=lb inter false Tell HLS that line-buffer reads/writes across iterations don't alias
#pragma HLS PIPELINE II=1 One pixel per cycle on the inner loop
#pragma HLS LOOP_TRIPCOUNT min=A max=B Required on every parametric loop so the latency report shows numbers, not ?

Why streaming, not nested loops over full intermediate arrays

A common anti-pattern is to write each stage as a nested loop over the whole image, materialize the output in a static T buf[H*W] array, and have the next stage loop over that array. For a 2160×3840 image with unsigned short intermediates this is ~16 MB per buffer — far larger than on-chip BRAM. Vitis HLS either spills to off-chip memory or refuses to optimize, and the final design is sequential (no inter-stage overlap), reports unknown latency (? in the csynth report because II analysis fails across the inferred shared memory), and consumes 5–10× more LUT/FF for the same functionality.

The streaming pattern below uses ~2 * MAX_W line-buffer elements per stage (tiny) and runs all stages concurrently.

Padded-raster iteration with read/write gating

The window center at iteration (r, c) looks at pixels (r−1..r+1, c−1..c+1) for K=3. Naively this fails at the image boundary. The canonical fix is to iterate over a (rows+K−1) × (cols+K−1) extended raster and gate reads and writes:

  • Read gate: read the next input pixel from the upstream stream only when r < rows && c < cols — i.e., on real-image coordinates. Off-image positions get a zero (or border-policy) pad value.
  • Write gate: emit the current window's output only when the window center maps to a real image pixel — typically when r >= K-1 && c >= K-1, so the very first valid output is the (K−1, K−1) iteration, corresponding to image pixel (0, 0).

This produces exactly rows × cols input reads and rows × cols output writes per stage, matches downstream token counts perfectly, and handles the K/2 startup latency of the line buffer naturally.

Complete Example (single-stage 3×3 box-blur scaffold)

The placeholder algorithm here is a 3×3 mean — the absolute simplest stencil. Replace the body of apply_kernel with the algorithm you actually want; the surrounding scaffold is what carries the streaming-stencil pattern.

// box3x3_stream.h
#include <hls_stream.h>
#include <ap_int.h>
#include <cstdint>

using u8 = std::uint8_t;
static constexpr int MAX_H = 2160;
static constexpr int MAX_W = 3840;

extern "C" void box3x3(const u8 *img_inp, u8 *img_out, int rows, int cols);

// box3x3_stream.cpp
#include "box3x3_stream.h"

// ---- Stage 1: raster-read input from m_axi into a stream ----
static void read_padded(const u8 *img_inp, int rows, int cols,
                        hls::stream<u8> &out) {
    for (int r = 0; r < rows; ++r) {
#pragma HLS LOOP_TRIPCOUNT min=1 max=MAX_H
        for (int c = 0; c < cols; ++c) {
#pragma HLS LOOP_TRIPCOUNT min=1 max=MAX_W
#pragma HLS PIPELINE II=1
            out.write(img_inp[r * cols + c]);
        }
    }
}

// ---- Stage 2: K=3 sliding-window stencil over the stream ----
//
// Iterates the extended raster (rows+2) x (cols+2). Reads input only on
// real-image positions; emits output only when the window center maps to
// a real image pixel. Line buffer caches the two most-recent rows; window
// holds the current 3x3 neighborhood as scalar registers.
static void stencil3x3(int rows, int cols,
                       hls::stream<u8> &in, hls::stream<u8> &out) {
    u8 lb[2][MAX_W];        // 2 line buffers, one element per column
#pragma HLS ARRAY_PARTITION variable=lb complete dim=1
#pragma HLS DEPENDENCE variable=lb inter false

    u8 w[3][3];             // 3x3 window as scalar registers
#pragma HLS ARRAY_PARTITION variable=w complete dim=0

    const int ER = rows + 2;   // extended-raster row count
    const int EC = cols + 2;   // extended-raster col count

    for (int er = 0; er < ER; ++er) {
#pragma HLS LOOP_TRIPCOUNT min=3 max=MAX_H+2
        for (int ec = 0; ec < EC; ++ec) {
#pragma HLS LOOP_TRIPCOUNT min=3 max=MAX_W+2
#pragma HLS PIPELINE II=1
            // ---- read gate: only on real-image coordinates ----
            u8 pix = 0;
            if (er < rows && ec < cols) {
                pix = in.read();
            }

            // ---- shift window left by one column ----
            w[0][0] = w[0][1]; w[0][1] = w[0][2];
            w[1][0] = w[1][1]; w[1][1] = w[1][2];
            w[2][0] = w[2][1]; w[2][1] = w[2][2];

            // ---- fetch new column from line buffer ----
            //   w[0][2] = pixel from row (er-2) at col ec  (lb row 0)
            //   w[1][2] = pixel from row (er-1) at col ec  (lb row 1)
            //   w[2][2] = pixel from row  er    at col ec  (the new one)
            u8 lb0 = lb[0][ec];
            u8 lb1 = lb[1][ec];
            w[0][2] = lb0;
            w[1][2] = lb1;
            w[2][2] = pix;

            // ---- shift line buffer up ----
            lb[0][ec] = lb1;
            lb[1][ec] = pix;

            // ---- apply the stencil kernel (REPLACE with your algorithm) ----
            //   Placeholder: 3x3 mean (sum / 9 ≈ (sum * 7281) >> 16)
            int sum = (int)w[0][0] + w[0][1] + w[0][2]
                    + w[1][0] + w[1][1] + w[1][2]
                    + w[2][0] + w[2][1] + w[2][2];
            u8 result = (u8)((sum * 7281) >> 16);

            // ---- write gate: only when window center is in-image ----
            //   The center of the window at (er, ec) corresponds to image
            //   pixel (er-1, ec-1). Emit iff that pixel is a real one.
            if (er >= 2 && ec >= 2) {
                out.write(result);
            }
        }
    }
}

// ---- Stage 3: raster-write output stream back to m_axi ----
static void write_cropped(u8 *img_out, int rows, int cols,
                          hls::stream<u8> &in) {
    for (int r = 0; r < rows; ++r) {
#pragma HLS LOOP_TRIPCOUNT min=1 max=MAX_H
        for (int c = 0; c < cols; ++c) {
#pragma HLS LOOP_TRIPCOUNT min=1 max=MAX_W
#pragma HLS PIPELINE II=1
            img_out[r * cols + c] = in.read();
        }
    }
}

// ---- Top function: connect stages via streams under DATAFLOW ----
extern "C" void box3x3(const u8 *img_inp, u8 *img_out, int rows, int cols) {
#pragma HLS INTERFACE m_axi  port=img_inp bundle=gmem0 depth=16384
#pragma HLS INTERFACE m_axi  port=img_out bundle=gmem1 depth=16384
#pragma HLS INTERFACE s_axilite port=rows    bundle=control
#pragma HLS INTERFACE s_axilite port=cols    bundle=control
#pragma HLS INTERFACE s_axilite port=return  bundle=control

#pragma HLS DATAFLOW

    hls::stream<u8> s_read("s_read");
    hls::stream<u8> s_filt("s_filt");
#pragma HLS STREAM variable=s_read depth=64
#pragma HLS STREAM variable=s_filt depth=64

    read_padded(img_inp, rows, cols, s_read);
    stencil3x3(rows, cols, s_read, s_filt);
    write_cropped(img_out, rows, cols, s_filt);
}

Extending to multi-pass pipelines

For a pipeline of N stencil stages (e.g., smoothing followed by gradient followed by suppression), declare N+1 streams under one #pragma HLS DATAFLOW and chain them. Each stage keeps its own private line buffer and window; do not share buffers across stages, and do not materialize a full intermediate image.

#pragma HLS DATAFLOW
hls::stream<u8>  s0, s1, s2, s3;
read_padded (img_inp, rows, cols, s0);
stage_A     (rows, cols, s0, s1);   // own lb/window for stage A
stage_B     (rows, cols, s1, s2);   // own lb/window for stage B
stage_C     (rows, cols, s2, s3);   // own lb/window for stage C
write_cropped(img_out, rows, cols, s3);

Each stage's read-gate / write-gate is identical to the single-stage version. Token counts match across stages because every stage produces exactly rows × cols outputs from rows × cols inputs.

Required Pragmas

Pragma Required? Purpose
#pragma HLS DATAFLOW on top function Yes Stages run concurrently, not sequentially
#pragma HLS PIPELINE II=1 on inner stencil loop Yes One pixel per cycle throughput
#pragma HLS ARRAY_PARTITION variable=lb complete dim=1 Yes Allow K parallel line-buffer row reads per cycle
#pragma HLS ARRAY_PARTITION variable=w complete dim=0 Yes Keep window cells in registers
#pragma HLS DEPENDENCE variable=lb inter false Yes Without this II=1 fails — HLS can't prove safe reuse
#pragma HLS LOOP_TRIPCOUNT min=A max=B Yes csynth report needs it to compute concrete latency
#pragma HLS STREAM variable=s_xx depth=N Optional Default FIFO depth (2) is fine for matched producer/consumer rates
#pragma HLS INTERFACE m_axi port=... depth=N Yes depth must match the testbench buffer size

When to Apply This Pattern

Is the kernel a 2D sliding-window operation on an image?
├── Yes → Streaming Image Stencil (this pattern)
└── No
    ├── 1D sliding window on a stream? → FIR / DSP-intrinsics pattern
    ├── Per-pixel point operation? → Simple PIPELINE II=1, no line buffer needed
    └── Random-access image traversal? → Cannot stream; consider tiling

Common Pitfalls

Pitfall Symptom Fix
No #pragma HLS DATAFLOW Sequential execution, latency report = ?, util 5–10× too high Add DATAFLOW on the top function and connect stages with hls::stream channels
static T buf[H*W] intermediate BRAM blowup or off-chip spill, II=1 unmet Replace with hls::stream<T> between stages
Missing DEPENDENCE inter false on lb csynth warns "II=1 not met, II=2 used" or similar Add the pragma — the read+write on the same column happens in the same iteration, so cross-iteration dependence is safe
ARRAY_PARTITION variable=lb cyclic factor=1 instead of complete dim=1 Sometimes works but verbose; on wide line buffers can generate excess MUXes Prefer complete dim=1 to partition by row
LOOP_TRIPCOUNT max=H*W (product expression) Vitis HLS sometimes can't resolve symbolic products → latency reports ? Use simple sums: max=MAX_H and max=MAX_W on the two separate loops
Read without gating Token mismatch — agent reads off-image and the upstream stream blocks Read only when r < rows && c < cols
Write without gating Output count != rows*cols, downstream blocks Emit only when window center is in-image (typically er >= K-1 && ec >= K-1)
Sharing one line buffer across stages Logically wrong (stages run concurrently with different row offsets) Each stage gets its own private line buffer and window
m_axi depth mismatch with testbench buffer cosim deadlocks or fails Set depth= to exactly the testbench buffer size (e.g. 16384 for a 128×128 testbench)

Resource vs Performance Trade-offs

Choice Performance Resource
PIPELINE II=1 + line buffer + DATAFLOW 1 pixel/cycle, ~rows×cols latency ~2 line buffers of MAX_W per stage in BRAM
PIPELINE II=2 (relaxed) 0.5 pixel/cycle Less aggressive partitioning, smaller LUT/FF
No DATAFLOW (sequential stages) N× slower for N stages, no overlap Often larger due to materialized intermediates
Wider word type (e.g. unsigned short for mag+dir packed) Same throughput Wider line buffers, larger BRAM

Related Patterns

  • Dataflow Diamond — for fork/join topologies (e.g., when one stage feeds two parallel paths that later merge)
  • Free Running Pipeline — for stages that consume/produce at different rates
  • Pointer Streaming — for m_axi → stream conversion patterns
  • Array Stencil Pragma — for the niche #pragma HLS ARRAY_STENCIL mechanism (different from this pattern; uses non-streaming nested loops on bounded arrays)
